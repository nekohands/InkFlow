# ADR 0024：首个注册账号的管理员引导规则

- 状态：Accepted for 1.0 Release Candidate
- 日期：2026-09-02
- 范围：Identity / Authentication / Authorization

## 背景

公开注册已经能够创建可登录的 `User`，但原实现把所有注册账号固定为 `Reader`，没有定义部署后的首个
管理员如何产生。仅在应用层先查询用户数量再插入会产生并发竞态；由客户端提交角色则会把管理员权限变成
不可信输入。

## 决策

1. 第一条成功持久化的注册账号获得 `Administrator`；之后的公开注册账号获得 `Reader`。
2. 注册接口不接收角色字段。`User.Create` 的默认角色仍为 `Reader`，用于非注册场景；公开注册统一经过
   `IUserRepository.AddRegistrationAsync`，由持久化边界决定角色。
3. PostgreSQL 实现为每次注册开启事务，取得固定键的事务级 advisory lock，在锁内重新检查重复邮箱和
   是否已有用户，再写入并提交。重复邮箱返回既有注册失败结果，不创建会话。
4. Administrator 复用现有 Administrator-only policy、Operator/Administrator policy 和 Administrator
   资源授权绕过规则，因此拥有当前应用范围内的全部管理员权限；该决定不新增超出现有模型的权限。
5. 既有账号不因本规则被追溯提权。数据库直接写入/测试夹具使用普通 `AddAsync`，不伪装成公开注册流程。

## 考虑过的方案

- 应用层 `COUNT/INSERT`：拒绝；多个 API 实例可同时观察到空库并创建两个管理员。
- 客户端传入角色：拒绝；任何未认证或低权限客户端都不应决定自身角色。
- Migration/启动脚本预置管理员：拒绝；无法表达“首个成功注册者”，且会引入预置凭据和部署时机问题。

## 后果

- 空数据库可通过一次正常注册完成安全边界明确的管理员引导，后续注册默认降为读者。
- 注册路径增加一次事务级全局锁和锁内查询；这是低频引导操作，优先保证跨实例正确性。
- 首个账号拥有高影响权限，生产部署必须配合强密码、注册限流、受控注册开放和管理员恢复治理；本 ADR
  不扩展为完整用户/角色管理或自动关闭注册流程。
- 规则只影响未来公开注册，不改变当前数据库中的用户角色。

## 验证

- Identity 单元测试覆盖首个管理员、后续 Reader、返回会话角色和重复注册。
- PostgreSQL 集成测试覆盖两个独立 DbContext 并发注册时恰好一个 Administrator、一个 Reader。
